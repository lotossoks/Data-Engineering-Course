# Практика 3. План преподавателя с готовыми SQL

Преподавательская версия студенческого плана: все SQL-заготовки заполнены, порядок заданий и бизнесовые задачи сохранены. Таблицы замеров оставлены пустыми. Копируйте SQL-блоки в DBeaver в подключение соответствующей СУБД и выполняйте по одному запросу. Подробный сценарий занятия: [сценарий преподавателя](Практика_3_сценарий_преподавателя.md).

## Бизнесовая задача

Интернет-магазин вырос, и разные команды обращаются к одним заказам по-разному:

- поддержка ищет один заказ по номеру;
- аналитики считают число и сумму оплаченных заказов по магазинам;
- руководитель магазина смотрит недельную сводку: число и сумму заказов своего магазина;
- CRM соединяет заказы со справочником клиентов для отчёта по городам.

Нужно выбрать систему и организацию таблиц для этих запросов. Сначала сравните PostgreSQL и ClickHouse на одинаковых данных, затем ускорьте запросы ClickHouse с помощью партиций и сортировки. После этого исследуйте распределение в Greenplum. Итог — заполненные таблицы наблюдений прямо в этом плане, рабочие таблицы и выбранные ключи для каждого запроса. Пустые ячейки заполняйте по ходу заданий; время указывайте в миллисекундах.

Это продолжение интернет-магазина из предыдущих занятий, но отдельный синтетический набор большего размера. В нём нет платежных операций. **Сумма заказов со статусом `paid` не означает подтверждённую оплату по правилам практики 2 и не является бухгалтерской выручкой.**

## Источники и зернистость

| Поле | Смысл |
|---|---|
| `order_id` | Уникальный номер заказа в исходном наборе |
| `customer_id` | Клиент; один клиент может иметь много заказов |
| `shop_id` | Магазин, новое поле для этой практики |
| `order_created_at` | Дата и время заказа, учебные данные в UTC |
| `status` | `paid` или `pending`; 90% заказов имеют статус `paid` |
| `total_amount` | Сумма одного заказа с точностью до копейки |

Одна строка `orders_*` — один заказ. В `customers` одна строка на клиента: `customer_id`, `city`. Поэтому JOIN с этим справочником не должен размножать заказы. `total_amount` хранится как `numeric(18,2)` в PostgreSQL/Greenplum и `Decimal(18,2)` в ClickHouse.

| Система | Подготовленные таблицы |
|---|---|
| PostgreSQL, база `shop` | `orders_small`: 1 000 строк; `orders_large`: 5 000 000 строк |
| ClickHouse, база `shop` | `orders_small` и `orders_large`: точные копии строк PostgreSQL |
| Greenplum, база `shop`, схема `public` | `orders_source`: 1 000 000 строк; `customers`: 100 000 клиентов |

В ClickHouse исходные таблицы имеют месячные партиции и сортировку `(shop_id, order_created_at, order_id)`. В PostgreSQL первичный ключ — `order_id`. Это выбранные конфигурации под разные нагрузки, а не универсальный рейтинг продуктов. Время заказа не возрастает вместе с номером заказа: это позволяет отдельно исследовать временные фильтры.

### Как измерять время в A1 и A2

Измеряйте один выделенный запрос, а не все блоки сразу. Для каждого запроса на каждой таблице сделайте четыре запуска: первый — прогрев, следующие три — измерения. Не запускайте параллельно загрузку данных.

**PostgreSQL:** добавьте перед измеряемым `select` строку `explain analyze` и выполните весь запрос:

```sql
explain analyze
select order_id, customer_id, status, total_amount
from orders_small
where order_id = 901;
```

В таблице результатов появится текст плана. В его конце найдите **`Execution Time: ... ms`** — это значение запишите в таблицу наблюдений. `Planning Time` не добавляйте. Выполните такой запрос четыре раза и записывайте время после каждого запуска. Для большой таблицы замените `orders_small` на `orders_large`; для A2 поставьте тот же `explain analyze` перед заполненным запросом агрегации. Для проверки самих ответов выполняйте SELECT без EXPLAIN.

**ClickHouse:** выполните обычный SELECT из соответствующего задания ниже четыре раза, сохраняя строку `settings ... log_comment = '...'` в конце запроса. Затем прочитайте время из журнала:


```sql
select event_time_microseconds, log_comment,
       query_duration_ms, read_rows, read_bytes
from system.query_log
where type = 'QueryFinish'
  and log_comment = 'p3_a_point_small'
order by event_time_microseconds desc
limit 4;
```

Если записи ещё не появились, выполните команду ниже и повторите запрос к журналу: 
```sql
system flush logs;
```

Для A3–A5 после серии запусков получите последние четыре записи каждой метки так:

```sql
-- Выполните после серии SELECT в том же подключении.
system flush logs;
```

```sql
select log_comment, query_duration_ms, read_rows, read_bytes, result_rows
from system.query_log
where type = 'QueryFinish' and startsWith(log_comment, 'p3_')
order by event_time_microseconds desc
limit 4 by log_comment;
```

Самая ранняя из четырёх попыток — прогрев; медиана следующих трёх.
QueryFinish: запрос успешно завершён; read_bytes — объём чтения, не размер таблицы.

Время находится в столбце **`query_duration_ms`**, уже в миллисекундах. Строки показаны от новой к старой: сверху вниз это **запуск 3, запуск 2, запуск 1, прогрев**. Для остальных запросов поменяйте метку:

| Запрос | Метка `log_comment` |
|---|---|
| A1, маленькая таблица | `p3_a_point_small` |
| A1, большая таблица | `p3_a_point_large` |
| A2, маленькая таблица | `p3_a_agg_small` |
| A2, большая таблица | `p3_a_agg_large` |

В измеряемых запросах ClickHouse `use_query_condition_cache = 0` отключает запоминание гранул, где фильтр не нашёл строк. Кеш данных остаётся включённым, поэтому прогрев по-прежнему полезен. Для новой серии после изменения запроса используйте новую метку `log_comment` и ту же метку в запросе к журналу, чтобы не смешивать разные варианты.

В таблицы записывайте серверное время указанным выше способом. Время в строке состояния DBeaver/DataGrip включает работу клиента.

### B1: как перекос влияет на выполнение

**Запрос аналитиков:** посчитать число и сумму всех заказов по магазинам. Данные и запрос одинаковы; меняется только распределение таблицы по сегментам.

**Куда смотреть, чтобы увидеть перекос:**

1. Найдите нижний узел **`Seq Scan on orders_customer`** или **`Seq Scan on orders_status`**. Он читает исходные строки до группировки.
2. Смотрите **`rows` внутри `(actual time=... rows=... loops=...)`**. В нашем Greenplum 7 для этого распределённого узла показан максимум числа строк, выданных одним сегментом. Это не сумма по кластеру. На проверенном стенде: **251 110** для `orders_customer` и **900 000** для `orders_status`.
3. Сопоставьте с равномерной нагрузкой: **1 000 000 / 4 = 250 000 строк на сегмент**. Около 251 тыс. близко к ней; 900 тыс. означает, что одному сегменту досталась почти вся работа. Точное распределение, включая пустые сегменты, показывает предыдущий запрос с `gp_segment_id`.
4. **`rows=250000` рядом с `cost` — оценка планировщика**, а не фактическое распределение. Не перепутайте её с `actual ... rows=900000`.
5. В `actual time=начало..конец` у Scan второе число — время завершения этого узла на показанном сегменте. Сравните его и итоговое `Execution Time` между таблицами. Время узлов не складывайте: их работа может перекрываться.

Сокращённые фрагменты нашего плана (время опущено):

```text
Seq Scan on orders_customer
  (cost=... rows=250000 ...) (actual time=... rows=251110 loops=1)

Seq Scan on orders_status
  (cost=... rows=250000 ...) (actual time=... rows=900000 loops=1)
```

Смотрите именно на **Scan до агрегации**: `rows=100` у агрегата — уже группы магазинов, по ним перекос исходных заказов не виден. Строки `Executor memory: ... avg ... max` описывают память, а не число обработанных заказов. Наличие `Motion` само по себе не доказывает skew.

## Как измерять

| Система | Способ | Что записывать |
|---|---|---|
| PostgreSQL | `explain analyze` перед запросом | `Execution Time` в конце плана |
| Greenplum | `explain analyze` | `Execution Time`; место Motion и читаемые партиции |
| ClickHouse | Обычный `select` с меткой `log_comment`, затем `system flush logs` и запрос к `system.query_log` | `query_duration_ms`, `read_rows`, `read_bytes` |
| ClickHouse, объяснение результата | `explain indexes = 1` | Отсечение parts / гранул; это не время выполнения |

В каждом сравнении: один прогрев, затем три измерения, чередуя варианты. Медиана трёх — среднее по порядку число после сортировки, не арифметическое среднее. Во время замеров дождитесь окончания загрузок и слияний. Не очищайте системный кеш и не запускайте несколько измерений одновременно.

В `system.query_log` берите только `QueryFinish`. Метка `log_comment` различает запросы, сортировка по времени — повторы. Последние четыре записи одной метки — три измерения и предшествующий прогрев. Значение `0 ms` означает ограничение точности журнала, а не бесплатный запрос; отношение времён с нулём не вычислять. Время внизу окна DBeaver включает клиентскую работу и может отличаться от серверного.

`explain analyze` добавляет расходы на измерение; серверные времена разных продуктов не являются строго одинаковой метрикой. Используем их для учебных тенденций с проверкой объёма работы, без обещания точного коэффициента ускорения.

Скорость не обязана отличаться в каждом отдельном запуске. Если время близко, сравните объём чтения и повторите серию без загрузок. Если результаты различаются, сначала исправьте логику или данные: ускорение неправильного ответа не считается результатом.

## Итоговое решение

Сформулируйте решение для каждого заказчика и укажите подтверждающие замеры:

| Чья задача | Где решали | Что объяснить в итоге |
|---|---|---|
| Поддержка: найти заказ по номеру | A1 и A5 | Как различается поиск в PG и CH; что изменил ключ по order_id в CH |
| Аналитики: число и сумма оплаченных заказов по магазинам | A2 | Как рост объёма изменил время агрегации в PG и CH; почему CH может быть быстрее без пропуска гранул |
| Руководитель магазина: недельная сводка | A4 | Почему ключ по магазину и времени уменьшил чтение; совпали ли число и сумма заказов |
| CRM: отчёт по городам клиентов | B2, подготовка B1 | Какой distribution уменьшает пересылку при JOIN и почему нужно проверить skew |

Дополнительно в A3 и B3 объясните, как партиции помогают месячному отчёту аналитиков по всем заказам. Для каждой пары сначала проверьте одинаковый ответ, затем сравнивайте время. Если разница времени неубедительна, отметьте это и сопоставьте объём чтения или Motion.

## Остановка и повторение

`docker compose stop` / `docker compose start` сохраняют данные. `docker compose down` удаляет контейнеры, но сохраняет именованные тома; следующий `docker compose up` подключит их. **`docker compose down -v` удаляет все данные только этого проекта, включая ваши таблицы.** Используйте полный сброс только осознанно, предварительно сохранив SQL и наблюдения. Не выполняйте глобальный Docker prune.

В SQL A3–A5 и B есть локальный повтор: `drop table if exists` удаляет только соответствующую учебную копию перед её созданием. Исходные таблицы при этом сохраняются. Если запустили часть задания повторно, проверьте число строк перед замерами.
