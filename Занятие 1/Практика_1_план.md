# Практика 1. Две витрины из одного источника

**Время:** Работайте по [стартовому ноутбуку](Практика_1_старт.ipynb) сверху вниз. Команды терминала выполняйте из папки `students`, SQL-проверки — в DBeaver, Python — в ноутбуке. После каждого блока покажите результат преподавателю.

## С чем хотим уйти

- Запускать локальные сервисы через Docker Compose и проверять их состояние.
- Читать исходные данные из PostgreSQL и проверять их в DBeaver.
- Получать одинаковую витрину двумя подходами: расчёт в pandas перед записью в ClickHouse и расчёт в ClickHouse после сохранения исходных строк в MinIO.
- Различать бакет, объект и ключ; понимать, почему запись `s3://...` не означает обычный путь к файлу.
- Сравнивать результаты и проверять, что повторная загрузка не создаёт дублей.

## Бизнесовая задача

Маркетингу интернет-магазина нужна чистая сумма заказов по кампаниям с учётом возвратов. Источник — заказы и привязки к кампаниям в PostgreSQL. Постройте в ClickHouse две витрины с одинаковыми полями: `campaign`, `paid_rub`, `returned_rub`, `net_rub`. Оплаченные заказы прибавляются, возвращённые вычитаются, ожидающие оплаты не учитываются. Возвраты в учебной задаче считаются полными.

```text
                         ┌─ pandas: расчёт ───────────────→ ClickHouse: campaign_revenue_pandas
PostgreSQL: 120 заказов ──┤
                         └─ raw Parquet → MinIO → SQL ClickHouse → campaign_revenue_s3
```

Значения подключений ниже нужны только для локального стенда.

| Сервис            | Адрес с компьютера      | База        | Пользователь | Пароль        |
| ----------------- | ----------------------- | ----------- | ------------ | ------------- |
| PostgreSQL        | `localhost:5433`        | `shop`      | `student`    | `studentpass` |
| ClickHouse (HTTP) | `localhost:8123`        | `de_course` | `student`    | `studentpass` |
| MinIO Console     | `http://localhost:9001` | —           | `minioadmin` | `minioadmin`  |
| MinIO API         | `http://localhost:9000` | —           | `minioadmin` | `minioadmin`  |

`localhost` — ваш компьютер. Внутри сети Docker Compose PostgreSQL слушает порт 5432, а ClickHouse обращается к MinIO по адресу `minio:9000`.

## Блок 1. Запустить стенд и проверить источник

**Что делаем.** Запускаем PostgreSQL, ClickHouse и MinIO. Docker Compose описывает их в одном файле и поднимает вместе. При первом создании пустого тома PostgreSQL автоматически выполняет `init.sql`: создаёт `orders` и `marketing_attribution`, затем загружает CSV. Вручную запускать SQL или импортировать CSV не нужно. В DBeaver создайте соединения с PostgreSQL и ClickHouse по таблице выше; откройте MinIO Console в браузере.

| Команда или действие | Зачем |
|---|---|
| `docker compose up -d` | Создать и запустить три сервиса в фоне. Первый запуск может занять несколько минут. |
| `docker compose ps` | Убедиться, что контейнеры работают и нужные порты опубликованы. |
| `docker compose logs postgres --tail 20` | Посмотреть последние сообщения PostgreSQL при проблеме запуска. Вместо `postgres` можно указать `clickhouse` или `minio`. |
| `SELECT`, `count(*)`, `GROUP BY`, `ORDER BY` | В DBeaver выбрать строки, посчитать их, сгруппировать по статусу и упорядочить результат. Составьте проверочные запросы самостоятельно. |

**Результат блока:** в PostgreSQL 120 заказов и 120 записей привязки к кампаниям; ClickHouse доступен из DBeaver, MinIO Console открывается. Объясните, почему сумму всех заказов нельзя назвать выручкой.

**Что делаем.** Откройте ноутбук в VS Code и выполните ячейки окружения и чтения PostgreSQL. Оба подхода должны использовать один и тот же набор исходных строк. `LEFT JOIN` по `order_id` сохраняет заказ даже без привязки к кампании.

| Команда или выражение | Зачем |

## Блок 3. Подход 1: рассчитать в pandas и загрузить 

**Что делаем.** Сгруппируйте исходные строки по кампании и статусу. Оставьте суммы для `paid` и `returned`, рассчитайте `net_rub` в TODO-ячейке. Затем загрузите готовые строки в `campaign_revenue_pandas` и проверьте таблицу в DBeaver. Статус `pending` в метрику не входит.

| Команда или выражение | Зачем |
|---|---|
| `pivot_table(index='campaign', columns='status', values='amount_rub', aggfunc='sum')` | Получить суммы по кампаниям и статусам. |
| `[['campaign', 'paid', 'returned']]` и `rename(columns={...})` | Оставить нужные статусы и привести имена к схеме витрины. |
| `clickhouse_connect.get_client(**CH)` | Подключиться к ClickHouse по HTTP. |
| `CREATE TABLE IF NOT EXISTS ...` | Создать учебную витрину, если её ещё нет. |
| `TRUNCATE TABLE de_course.campaign_revenue_pandas` | Очистить только первую учебную витрину перед загрузкой. |
| `ch.insert(...)` | Записать рассчитанные в pandas строки в ClickHouse. |

**Результат блока:** в первой витрине по одной строке на каждую из четырёх кампаний; поля `paid_rub`, `returned_rub`, `net_rub` заполнены. Покажите в DBeaver, что чистая сумма отражает разницу между оплатами и возвратами, и объясните, где произошло преобразование. В учебной выборке у каждой кампании есть оба нужных статуса, поэтому отдельно заполнять пропуски в сводной таблице не требуется.
 

## Блок 4. Подход 2: сохранить исходные строки в MinIO — 

**Что делаем.** Возьмите те же 120 строк и запишите их в Parquet **без группировки и расчёта метрики**. Загрузите файл как объект в MinIO. Найдите объект в Console и покажите его ключ и метаданные. Здесь pandas нужен только для записи Parquet, не для бизнес-расчёта.

| Команда или выражение | Зачем |
|---|---|
| `raw_df.to_parquet(buffer, engine='pyarrow', index=False)` | Сериализовать исходные строки в Parquet. |
| `boto3.client('s3', endpoint_url=...)` | Подключиться из ноутбука к локальному MinIO. |
| `s3.list_buckets()` / `s3.create_bucket(...)` | Проверить наличие бакета и создать его при необходимости. |
| `s3.put_object(Bucket=..., Key=..., Body=...)` | Загрузить объект; повтор с тем же ключом заменяет содержимое. |
| `s3.head_object(...)` | Получить размер и метаданные объекта без скачивания. |
| `s3('http://minio:9000/...', ..., 'Parquet')` | Прочитать объект из контейнера ClickHouse как таблицу. |

**Результат блока:** в бакете `de-course` виден Parquet-объект с ключом вида `raw/orders/load_date=.../orders.parquet`; ClickHouse читает из него 120 строк. Объясните, почему ноутбук обращается к `localhost:9000`, а ClickHouse — к `minio:9000`. Части ключа, похожие на папки, не делают S3 обычной файловой системой.

## Блок 5. Подход 2: рассчитать в ClickHouse 

**Что делаем.** ClickHouse читает Parquet из MinIO, группирует строки по кампаниям и записывает результат в `campaign_revenue_s3`. Исправьте TODO с `net_rub` в SQL-ячейке ноутбука.

| Команда или выражение | Зачем |
|---|---|
| `sumIf(amount_rub, условие)` | Суммировать значения только для нужного статуса. |
| `GROUP BY campaign` | Получить одну строку на кампанию. |
| `INSERT INTO ... SELECT ...` | Выполнить расчёт в ClickHouse и записать вторую витрину. |
| `TRUNCATE TABLE de_course.campaign_revenue_s3` | Удалить старые строки только из второй учебной витрины перед повторной загрузкой. |

**Результат блока:** вторая витрина содержит четыре кампании и получена из исходного Parquet, а не из уже рассчитанной таблицы pandas. Покажите её в DBeaver.

## Блок 6. Сравнить и повторить — 01:22–01:30

**Что делаем.** Прочитайте обе витрины с одинаковой сортировкой, сравните все столбцы. Повторно выполните **целиком** ячейки загрузки, включая очистку каждой учебной таблицы, и сравните снова.

| Команда или выражение | Зачем |

**Результат блока:** обе витрины идентичны по кампаниям и метрикам; повторная полная загрузка не создала дублей. Сохраните ноутбук и ответьте: чем различаются два подхода, какой относится к ETL, а какой — к ELT? Почему результат совпал? Что неидеально в схеме `TRUNCATE` + загрузка?
